# Configuration

Gitea Mirror has two configuration layers. Almost everything lives in the web interface and is stored in the database per user. A smaller set of environment variables covers the things that have to be known before the app can serve a request, such as the session secret and the public URL, and can additionally seed the database configuration on first boot.

Start with the web interface. Reach for environment variables when you want a deployment that comes up fully configured without anyone clicking through a form.

## The Configuration page

![The Configuration page showing the Connections tab](/assets/configuration.png)

The Configuration page is organized into four tabs.

### Connections

This is where the two ends of the mirror are set up: the **Sources** card for where repositories come from, and the destination card next to it.

**The Sources card** lists the hosts repositories are pulled from, and you can add more than one. **Add source** opens an editor: pick the host (GitHub, GitLab, Gitea / Forgejo or Git URL; all but GitHub carry a BETA pill), the instance URL for a self-hosted instance, the username, and a personal access token, with the scopes it needs listed next to the token field. A GitHub source can use a GitHub App installation instead of a token. Git URL is for hosts that can only be cloned and asks for the host instead. The repository selection options (private, public, archived, forks, repositories where you are only a collaborator, and starred repositories) are in the **Repository Selection** card below. The [Sources](/docs/sources/) page covers each host.

**The destination card** starts with the **Destination** dropdown: Gitea, Forgejo, GitHub or GitLab. Gitea is the default; the other three carry a BETA pill. For Gitea and Forgejo the card holds the server URL, an optional external URL, an access token and the username that acts as default owner. For GitHub and GitLab it holds the instance URL, the account and a token, and a notice explains that those targets are overwritten on every sync. The card also carries the organization settings: the mirror strategy, default organization, organization visibility, and the per-repository mirror interval that Gitea itself uses to re-pull from the source. The [Destinations](/docs/destinations/) page covers each host.

GitHub to Gitea is the supported path. Every other source and destination is beta: tested end to end against real hosts, with less time in the field.

Both cards have a **Test** button that performs a live authenticated call, so you can confirm credentials before importing anything.

**Locks.** Once repositories are imported the source locks, and once anything is mirrored the destination locks. The dropdown and the URL field then show a lock note with a **Change** button, and changing goes through a confirmation that spells out what happens to the existing repositories. Environment values that disagree with a locked host are ignored on boot with a warning.

If your Gitea instance is reachable at one URL from the Gitea Mirror process and at a different URL from your browser, for example an internal service name versus a public hostname, set the external URL as well. Dashboard links use the external URL while all API and mirroring traffic keeps using the primary URL.

### Mirror settings

Below the connection cards, the mirror settings decide what travels with the code: issues, pull requests, labels, milestones, security advisories, releases, wiki and LFS objects, plus the force push protection strategy. Switches that the current source or destination cannot serve are disabled and say why. LFS also needs LFS turned on in Gitea or Forgejo itself: `LFS_START_SERVER = true` in the `[server]` section of `app.ini`.

**Security advisories**, under **Metadata to mirror**, copies each published GitHub security advisory of a repository to its mirror. Gitea and Forgejo have no advisories of their own, so each one becomes an issue labeled `security-advisory` and titled with its id, for example `[GHSA-8jhw-6pjj-8723] Email verification links can redirect users to any website`, with the severity, CVE, affected and patched versions, credits and the advisory's text. The issue is updated when the advisory changes and closed if it is withdrawn. Draft advisories are never copied. It needs a GitHub source, costs one request per repository and sync, and is off by default.

Releases have two numbers under the switch. **Latest** is how many releases are mirrored per repository, newest first, ten by default. **Assets for latest** is how many of those get their assets uploaded: leave it empty to upload assets for every mirrored release, set it to `0` for release notes and tags only, or set it to a number to keep assets for the newest N releases while older ones keep their notes and tag. The limit never deletes assets that were already uploaded.

The **Remove old release assets** switch under them turns that last sentence around. Off, which is the default, a sync only ever uploads. On, every sync also deletes the attachments of each mirrored release ranked past **Assets for latest**, so lowering the limit actually frees the disk. It is global rather than per repository, it never removes a release or its notes, and a release whose attachments cannot be listed is left alone and retried on the next sync.

The **Pre-releases** switch under them decides which releases are candidates at all: left on it mirrors every release, turned off it skips everything the source marks as a pre-release. With a filter active the **Latest** count applies to the releases that match, so ten stable releases are kept even when a project ships betas in between, and releases of the other kind are removed from Gitea on the next sync. A release the destination has no pre-release flag for is left alone. The per organization and per repository **Mirror options** dialog offers the same choice under its **Releases** row - **All**, **Stable only**, or **Inherit**, where **Inherit** means the level above - and the release type is `RELEASE_TYPE` in the environment.

While pre-releases are on, **At most** under the switch caps how many of the **Latest** releases may be pre-releases. Empty means pre-releases count like any other release. With **Latest 10** and **At most 3** the mirror keeps the three newest pre-releases and the seven newest stable releases, looking up to 1,000 releases back for them, so a project that publishes a build every night still has its stable releases on Gitea. `0` keeps no pre-releases. Pre-releases past the cap are removed from Gitea on the next sync, the newest kept. The per organization and per repository dialog has the same **Pre-release limit** field, and in the environment it is `RELEASE_PRERELEASE_LIMIT`.

**Custom tag rules...** beside that switch opens a dialog with **Include tags** and **Exclude tags**, two comma separated pattern lists that catch the projects shipping release candidates without marking them as pre-releases. The same lists sit under the **Releases** row in the per organization and per repository dialog, where leaving both lists empty means the level above, and in the environment they are `RELEASE_INCLUDE_TAGS` and `RELEASE_EXCLUDE_TAGS`.

Opened from a repository, that dialog also lists the releases Gitea already holds for it and crosses out the ones the draft rules would drop on the next sync, so a pattern can be checked before saving. The organization and global dialogs leave the list out because their rules apply to many repositories at once.

### Automation

This tab controls scheduled mirroring and cleanup.

Scheduled syncing runs on an interval or a cron schedule. When enabled it re-syncs existing mirrors, and optionally discovers newly created GitHub repositories and mirrors them without any manual action. Two switches on the schedule card govern that: **Auto-import new repositories** decides whether new repositories are discovered and added to the database, and **Auto-mirror new repositories** decides whether they are then actually mirrored to Gitea. With auto-import off, syncs only update the repositories you already have, and the import button at the top of the page brings in new ones when you want them.

The same tab holds repository cleanup, which handles repositories that have disappeared from the source. The action for an orphaned repository is one of `skip`, `archive`, or `delete`, and `archive` is the default because it preserves the mirrored data. There is a dry-run mode that logs what would happen without touching anything, and a **Run now** button that checks right away instead of at the next check. The card's **Reconcile with destination** button compares a Gitea or Forgejo server with the database and offers to adopt mirrors the app does not know about or reset rows whose mirror is gone. Both are described on the [Cleanup and reconcile](/docs/cleanup-and-reconcile/) page.

### Notifications

Gitea Mirror can send a notification on sync failure, on sync success, and when a new repository is discovered. Four providers are supported: ntfy, Apprise, Gotify, and a generic webhook. Each has its own settings, and only one provider is active at a time.

The generic webhook sends a JSON POST containing `title`, `message`, `type`, and `timestamp` fields, which makes it straightforward to wire into anything that accepts an inbound hook.

### Authentication

This tab configures how people sign in. Email and password authentication is always available. On top of that you can register OIDC or SSO providers, and enable header authentication for deployments sitting behind a reverse proxy that already handles identity, such as Authentik or Authelia.

Header authentication reads the username, email, and display name from configurable request headers. It can optionally auto-provision accounts on first sight of a new user, restricted to an allowlist of email domains.

The **API Keys** card on the same tab creates keys for scripts and CI pipelines. A key is sent in the `x-api-key` header and can call every endpoint the web interface uses. See [API and API keys](/docs/api/).

> **Warning:** Only enable header authentication when the app is genuinely behind a trusted proxy that strips those headers from inbound client requests. If clients can set the headers themselves, anyone can sign in as anyone.

## Mirror strategies

The mirror strategy decides where each repository lands on the destination. There are four, and they are set on the destination card. The examples below say Gitea and organization; on GitLab the equivalent is a group, and the GitHub target uses organizations that must already exist.

### preserve

Keeps the same organization structure as the source. A repository at `acme/api` on GitHub becomes `acme/api` in Gitea, with the organization created if it does not exist. This is the default and the right choice when you want the mirror to be recognizable to anyone who knows the source side.

### single-org

Consolidates every repository into one Gitea organization, regardless of where it came from on the source. The target organization defaults to `github-mirrors`. Useful when you want all mirrored content in one clearly separated namespace.

### flat-user

Places every repository directly under your Gitea user account, with no organizations involved. The simplest layout, and a reasonable fit for a personal instance with a modest number of repositories.

### mixed

Splits the difference. Your personal repositories go into a single named organization, while repositories owned by organizations on the source preserve their original structure. This keeps organization repositories where people expect them while corralling your personal ones.

> **Note:** Repositories mirrored because you starred them have their own setting, **Starred repository destination**. **Dedicated organization** puts them all in one organization, named `starred` by default. **Preserve source owner** puts each under its GitHub owner's name, whatever the strategy above says. **Same as other repos** places them like any other repository, so the strategy, an organization's destination and a repository's own destination apply to them too. When a starred repository would take a name already used by a different repository in the same place, the duplicate strategy setting adds the owner's name as a suffix or a prefix.

### Moving existing mirrors after a change

A new strategy, organization destination or starred setting applies to repositories mirrored from then on. Mirrors that already exist stay where they were created and keep syncing there. When some of them are not where the current settings would put them, the footer of the **Organization Structure** card says how many, with a **Review and move** button. This works on Gitea and Forgejo destinations; on GitHub and GitLab the footer only says the strategy applies to new repositories.

**Review and move** checks each of those mirrors on the destination and shows what a move would do, before anything changes:

- **Will move**, grouped by the new owner. An owner that does not exist yet is marked **new organization** and is created first. A mirror marked **nothing to move** is already in the right place, for example because someone moved it there by hand, or because a mirror of the same repository already sits there; only Gitea Mirror's record changes, and the other copy is left for you to delete.
- **Blocked**, with the reason and what to do about it: the target name is taken by another repository, the owner is a person's account rather than an organization, the owner is a name the destination keeps for itself, your destination account cannot create repositories in that organization or transfer the repository, or the mirror is not on the destination at all. Blocked mirrors stay where they are and keep syncing.
- **Left out**: mirrors with a sync or mirror run going on, mirrors archived after their source disappeared, mirrors whose source is gone while cleanup waits, and mirrors made on a previous destination.

**Use the source name**, on by default, gives each moved mirror its source repository's name, the way a new mirror would get it. When that name is taken at the new owner, the mirror keeps its current name if that one is free, and is blocked otherwise. Gitea Mirror never makes up a new name during a move. Turn the switch off to keep every mirror's current name.

**Move** checks each mirror again right before moving it, and moves only the ones whose target is still the one you saw. Each mirror is transferred, and renamed when needed, with its history, issues and mirror settings; nothing is deleted or downloaded again. The record is updated after every step, so a failure halfway leaves Gitea Mirror pointing at wherever the mirror ended up. The run stops after three destination errors in a row. You can close the dialog while it runs; the card shows the progress, and the [activity log](/docs/repositories-and-organizations/#activity-log) gets a line per mirror.

Old links and clones keep working after a move: the destination sends the old address on to the new one until another repository takes that name. Access given through the old organization's teams does not come along, and organizations left empty stay on the destination.

## Schedule intervals

Anywhere Gitea Mirror asks for an interval, it accepts several formats:

- A duration string with a unit: `30m`, `8h`, `7d`. The recognized units are `ms`, `s`, `m`, `h`, `d`, and `w`, and both short and long spellings work, so `8h` and `8 hours` are equivalent.
- A five-field cron expression: `0 2 * * *` for daily at 2 AM, `0 */6 * * *` for every six hours, `0 0 * * 0` for weekly on Sunday at midnight.
- A plain number, interpreted as seconds. `3600` means one hour.

Cron expressions are useful when you want syncing to happen during a specific low-traffic window rather than at a fixed offset from whenever the service last restarted.

## Configuring through environment variables

Environment variables serve two distinct purposes, and it is worth keeping them apart.

The first group is read directly by the running process at startup and has no equivalent in the UI: the port, the host, the session secret, the encryption secret, and the public URLs. These must be set as environment variables.

The second group seeds the database configuration. On startup, if any of `GITHUB_USERNAME`, `GITHUB_TOKEN`, `GITEA_URL`, `GITEA_USERNAME`, or `GITEA_TOKEN` is set, Gitea Mirror loads the whole environment configuration and writes it into the first user's config row. If no user exists yet, it does nothing and tries again on the next start. `ENVIRONMENT_SEEDING=true` loads it without any of those five, so tokens can stay in the UI, and `ENVIRONMENT_SEEDING=false` turns it off. See [How environment configuration is applied](/docs/environment-variables/#how-environment-configuration-is-applied).

> **Note:** A variable that is set overwrites the matching field in the database on every start. If you set `GITEA_ORGANIZATION` in your compose file and then change the organization through the UI, the next restart puts the environment value back. Variables you leave unset do not touch what the UI saved. Either manage a setting through the UI or through the environment, not both.

Tokens supplied through the environment are encrypted with AES-256-GCM before they are stored, the same as tokens entered through the UI.

The source and destination hosts are seeded the same way: `SOURCE_PROVIDER` and `SOURCE_URL` pick the source, `DESTINATION_PROVIDER` picks the destination, and the `GITHUB_*` and `GITEA_*` names keep working for every host. A `SOURCE_PROVIDER`, `SOURCE_URL` or `GITEA_URL` value that disagrees with a locked host is ignored with a warning rather than applied.

## Core environment variables

These are the ones that matter for nearly every deployment. The [environment variables reference](/docs/environment-variables/) has the complete list.

### Server

| Variable | Default | Description |
| --- | --- | --- |
| `NODE_ENV` | `development` | Runtime environment. The container image sets `production`. |
| `HOST` | `0.0.0.0` | Interface to bind. |
| `PORT` | `4321` | Port to listen on. |
| `BASE_URL` | `/` | Path prefix when the app is served under a subpath, for example `/mirror`. |
| `DATABASE_URL` | `sqlite://data/gitea-mirror.db` | SQLite database location. The container image sets `file:data/gitea-mirror.db`. |

> **Note:** `DATABASE_URL` accepts the `sqlite://` scheme, the legacy `file:` scheme, or a plain path. Relative paths resolve against the process working directory and the parent directory is created if it is missing. Point it at a mounted volume to relocate the database. gitea-mirror only supports SQLite, so any other scheme, such as `postgresql://`, is ignored with a warning and the default location is used.

### Authentication and secrets

| Variable | Default | Description |
| --- | --- | --- |
| `BETTER_AUTH_SECRET` | generated in Docker and Nix | Signs session cookies. Generate with `openssl rand -base64 32`. Required for a bare metal install. |
| `BETTER_AUTH_URL` | `http://localhost:4321` | The origin the auth server runs on. Scheme and host only, no path. |
| `BETTER_AUTH_TRUSTED_ORIGINS` | none | Comma-separated list of additional origins allowed to make auth requests. |
| `ENCRYPTION_SECRET` | generated in Docker and Nix | Key for AES-256-GCM encryption of stored GitHub and Gitea tokens. Generate with `openssl rand -base64 48`. Falls back to `BETTER_AUTH_SECRET` when unset. |

`BETTER_AUTH_SECRET` and `ENCRYPTION_SECRET` are both generated by the Docker entrypoint and by the Nix package if you leave them unset, and kept in the data directory so they survive restarts. A bare metal install generates nothing. Without `BETTER_AUTH_SECRET`, Better Auth falls back to a public default secret and refuses to run with it in production. Without `ENCRYPTION_SECRET`, tokens are encrypted with `BETTER_AUTH_SECRET`, so changing that secret later makes every stored token unreadable. Set both, and keep them the same across restarts.

The origin of `BETTER_AUTH_URL` is trusted automatically, so `BETTER_AUTH_TRUSTED_ORIGINS` is only for additional origins. Common reasons to add one: reaching the app by local IP as well as by domain name, an external SSO provider, or a reverse proxy on a different hostname.

Reaching the app at more than one address, serving it under a path prefix and running it behind a proxy are covered in [Reverse proxy and URLs](/docs/reverse-proxy/).

## Example: fully declared deployment

A compose file that comes up ready to mirror, with no UI interaction required:

```yaml
services:
  gitea-mirror:
    image: ghcr.io/raylabshq/gitea-mirror:latest
    container_name: gitea-mirror
    restart: unless-stopped
    ports:
      - "4321:4321"
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true
    volumes:
      - ./data:/app/data
    environment:
      - NODE_ENV=production
      - HOST=0.0.0.0
      - PORT=4321
      - BETTER_AUTH_SECRET=${BETTER_AUTH_SECRET}
      - BETTER_AUTH_URL=https://gitea-mirror.example.com
      - BETTER_AUTH_TRUSTED_ORIGINS=https://gitea-mirror.example.com
      - ENCRYPTION_SECRET=${ENCRYPTION_SECRET}

      - GITHUB_USERNAME=your-username
      - GITHUB_TOKEN=${GITHUB_TOKEN}
      - PRIVATE_REPOSITORIES=true
      - MIRROR_STARRED=true

      - GITEA_URL=https://gitea.example.com
      - GITEA_USERNAME=admin
      - GITEA_TOKEN=${GITEA_TOKEN}
      - MIRROR_STRATEGY=preserve

      - MIRROR_METADATA=true
      - MIRROR_ISSUES=true
      - MIRROR_RELEASES=true

      - SCHEDULE_ENABLED=true
      - SCHEDULE_INTERVAL=8h
      - AUTO_IMPORT_REPOS=true
      - AUTO_MIRROR_REPOS=true
```

Remember that the configuration is only written once an admin account exists. Sign up first, then restart the container, or simply let the next scheduled restart pick it up.
