# Authentication

Gitea Mirror handles sign-in through [Better Auth](https://better-auth.com) with session cookies. Three methods can get a user into the app: email and password, single sign-on against an external identity provider, and header authentication behind a reverse proxy. Email and password is always available. The other two are additive, so turning on SSO does not switch off the local login.

Gitea Mirror can also act as an OIDC provider for other applications, which is covered at the end of this page.

## Email and password

This method is always enabled and needs no configuration.

### Creating the first account

Visit `/signup` on a fresh instance and create an account. That account owns the instance configuration, which is what "first user becomes admin" means in practice.

Once one account exists, `/signup` redirects to `/login` and the sign-up endpoint refuses new accounts, so a public instance cannot accumulate accounts on its own. Additional users are created through header auth provisioning or SSO, which only creates accounts for emails in the provider's Domain (see [New accounts through SSO](#new-accounts-through-sso)). `AUTH_ALLOW_SIGNUP=true` keeps the sign-up endpoint (`POST /api/auth/sign-up/email`) open for scripts; the `/signup` page still redirects once an account exists.

### Sessions

Sessions are cookie based. The cookie is named `better-auth.session_token` and lasts 30 days, refreshed as the user stays active.

### Resetting a password

There is no email-driven password reset flow, because Gitea Mirror does not send email. Reset from the command line instead:

```bash
bun run reset-password -- --email=user@example.com --new-password='new-secure-password'
```

> **Note:** Accounts in Gitea Mirror are never email-verified, since no verification flow exists. This matters for SSO account linking, described below.

### Two-factor authentication

With two-factor authentication (2FA), an account with a password can also ask for a code from an authenticator app, such as 1Password, Google Authenticator, Authy or Aegis, each time it logs in.

To turn it on, open the account menu (your avatar, top right), choose **2FA** (it shows **Set up**) and enter your password. Scan the QR code with the app, or type the key shown under it, and enter the 6-digit code the app shows. You then get ten backup codes: copy or download them and keep them somewhere safe, like a password manager. They are only shown once.

From then on, logging in with your password asks for the current code from the app. **Use a backup code** takes one of the saved codes instead; each works once. **Trust this device for 30 days**, off by default, skips the code in that browser until then.

- Five wrong codes in one login send you back to the password. Ten wrong codes in a row lock code entry for 15 minutes.
- Once it is on, the menu item shows a switch. Flipping it off asks for your password and turns 2FA off; setting it up again takes a new QR code. The same dialog has **New backup codes**, which replaces the old ones and also asks for your password.
- 2FA guards the email and password login only. SSO accounts use their identity provider's own two-factor, header auth trusts the proxy, and API keys work as before. An application that signs in through Gitea Mirror as an OIDC provider gets the code step on the login page like anyone else.
- The app's secret and the backup codes are stored encrypted with `BETTER_AUTH_SECRET`. If that secret changes, codes stop working until two-factor is turned off and set up again.

If both the phone and the backup codes are gone, turn 2FA off from the command line, the same way as [resetting a password](#resetting-a-password). It also forgets the devices that were trusted:

```bash
bun run disable-2fa -- --email=user@example.com
```

### Required secret

Set `BETTER_AUTH_SECRET` to a random string of at least 32 characters. It signs session tokens.

```bash
openssl rand -base64 32
```

If you leave it unset, the Docker entrypoint generates one and stores it in `/app/data/.better_auth_secret` so sessions survive a restart. Losing that file logs everyone out.

### URL configuration

Better Auth validates the origin of every request, so it needs to know your real external URL.

| Variable | Purpose |
|---|---|
| `BETTER_AUTH_URL` | The external origin of the instance, for example `https://mirror.example.com`. |
| `BETTER_AUTH_TRUSTED_ORIGINS` | Comma-separated extra origins allowed to submit auth requests. |
| `BASE_URL` | Path prefix when the app is served under a subpath, for example `/mirror`. |

> **Warning:** Behind a reverse proxy, set `BETTER_AUTH_URL` and `BETTER_AUTH_TRUSTED_ORIGINS` to your external HTTPS URL. See [Reverse proxy and URLs](/docs/reverse-proxy/). A mismatch usually shows up as a 500 error or an invalid origin message right after login.

The app also auto-detects the origin from the incoming `X-Forwarded-Host` and `X-Forwarded-Proto` headers, which covers many proxy setups without extra configuration. Setting the variables explicitly is still the reliable path.

## Single sign-on

SSO lets users authenticate against an external identity provider such as Google, Okta, Authentik, or Azure AD. Providers are managed under **Configuration > Access**, in the **Identity Providers** panel: click **Add provider**.

Only the instance owner, the first account created on the instance, can add, change or remove providers, and they see every provider. A provider applies to every account: anyone whose email is in its Domain can sign in through it, and an existing account with that email is linked to it. Other accounts see the panel as managed by the owner, and the provider API answers them with 403.

Earlier versions let any account add a provider. If another account added one on your instance, it shows a warning in the panel and nobody can sign in with it until you edit and save it. Accounts with a sign-in linked through such a provider, or through one that had already been deleted, were signed out once by the upgrade, and their API keys were turned off: they stay in the list as inactive, so check for any you do not recognize and create new ones. Delete any provider you do not recognize.

Use OIDC. The dialog also has a SAML 2.0 tab, but SAML sign-in does not work in the current release, see [SAML 2.0 providers](#saml-20-providers).

### Shared fields

Every provider, regardless of protocol, needs these:

| Field | Description |
|---|---|
| Issuer URL | The identity provider's issuer, for example `https://accounts.google.com`. Keep any trailing slash your provider shows. |
| Domain | The email domain this provider serves. Multi-domain providers take a comma-separated list. This field controls account linking and who can get a new account through SSO, see below. |
| Provider ID | A short unique slug such as `google-sso`. It appears in the callback URL, so pick it before configuring the upstream provider. |

### OIDC providers

Add these on top of the shared fields:

| Field | Description |
|---|---|
| Client ID | OAuth client ID issued by your provider. |
| Client Secret | OAuth client secret. |
| Scopes | Defaults to `openid`, `email`, `profile`. |
| PKCE | Enabled by default. Leave it on unless your provider cannot handle it. |

Enter the Issuer URL and click **Discover** to fetch the authorization, token, JWKS, and userinfo endpoints automatically. Set Domain yourself: it is your users' email domain, not the provider's hostname. The form and the provider list warn when Domain is the provider's hostname, which older versions of Discover filled in.

Saving a provider fetches its discovery document unless all four endpoints and the scopes are already filled in. The dialog only has fields for the authorization and token endpoints, so a provider without a discovery document has to be added through the API: a `POST` to `/api/sso/providers` with `authorizationEndpoint`, `tokenEndpoint`, `jwksEndpoint`, `userInfoEndpoint` and `scopes` set.

When you edit a provider, the Provider ID is locked, and leaving Client Secret empty keeps the saved secret.

> **Warning:** Google rejects the `offline_access` scope. Remove it from the scope list for Google providers or the sign-in fails.

The redirect URL to register with your provider is:

```text
https://your-domain.com/api/auth/sso/callback/{provider-id}
```

Replace `{provider-id}` with the Provider ID you chose. The UI shows the exact URL as you type, so you can copy it straight into the provider console.

#### Example: Google

1. In Google Cloud Console, create an OAuth 2.0 Client ID.
2. Add `https://your-domain.com/api/auth/sso/callback/google-sso` as an authorized redirect URI.
3. In Gitea Mirror, set Issuer URL to `https://accounts.google.com`, Provider ID to `google-sso`, Domain to your company email domain, then paste the client ID and secret.
4. Click **Discover**, then save.

#### Example: Authentik

1. Create an Application and an OIDC Provider in Authentik.
2. Start adding the provider in Gitea Mirror so you can copy the redirect URL it displays.
3. Paste that redirect URL into the Authentik provider, then finish creating it.
4. Back in Gitea Mirror, paste the issuer URL, client ID, and client secret, click **Discover**, and set Domain to the email domain your Authentik users actually have.

### SAML 2.0 providers

> **Warning:** SAML sign-in does not work in the current release. The SAML 2.0 tab saves the provider through the OIDC path, so the SAML settings below are not stored. Use OIDC if your identity provider offers it.

The SAML 2.0 tab asks for:

| Field | Description |
|---|---|
| SAML Entry Point | Your identity provider's SSO URL, where authentication requests are sent. |
| X.509 Certificate | The signing certificate from your identity provider, used to validate assertions. |
| Callback URL | Optional. Where users are sent after a successful sign-in. |

The assertion consumer service URL is:

```text
https://your-domain.com/api/auth/sso/saml2/sp/acs/{provider-id}
```

Gitea Mirror also publishes service provider metadata, which many identity providers can import directly:

```text
https://your-domain.com/api/auth/sso/saml2/sp/metadata?providerId={provider-id}
```

The default name ID format is `urn:oasis:names:tc:SAML:1.1:nameid-format:emailAddress`, which keeps identities aligned with the email-based account matching described next.

### New accounts through SSO

Once an account exists, signing in through SSO with an email that has no account yet only creates one when the email belongs to one of the provider's domains, or a subdomain of one. Anyone else lands on an error page with `SIGNUP_CLOSED`.

This keeps a provider that anyone can sign up at, such as Google, from letting every account there in. To let anyone the provider knows get an account, set `AUTH_ALLOW_SIGNUP=true`, which also opens email sign-up.

### Account linking

When someone signs in through SSO with an email that already has a local account, Gitea Mirror links the two so they land on the same data instead of getting a duplicate account or an error page. Matching is by email address.

The trust model is scoped to the Domain field you set on the provider:

- Registering a provider marks it as verified for the domains you listed.
- A sign-in is auto-linked only when the user's email actually belongs to one of those domains. A cross-domain email is refused even though the provider is registered, and even when the provider says the email is verified.
- Local accounts are never email-verified in this app, so the linker deliberately does not require local verification. Otherwise linking could never happen.

> **Warning:** Set Domain to the email domains your identity provider genuinely issues. If that provider lets users self-register or claim arbitrary addresses within the domain, someone there can claim an address matching a local account and take it over. Registering a provider means vouching for its identity model for those domains.

### Signing in

When at least one provider is configured, the login page shows **Email** and **SSO** tabs. On the SSO tab a user either clicks a provider button or enters their work email, which routes them to the provider matching that email domain.

## Header authentication

Header authentication trusts an upstream reverse proxy such as Authentik, Authelia, oauth2-proxy, or Traefik forward-auth to authenticate the user and pass identity along in HTTP headers. There is no login form and no callback: Gitea Mirror reads the headers and resolves the user.

This method is configured through environment variables only, never in the UI. Trusting a header means trusting whoever can set it, and that is a decision for whoever controls the proxy, not for a user logged into the app.

### Environment variables

| Variable | Description | Default |
|---|---|---|
| `HEADER_AUTH_ENABLED` | Master switch, must be `true` to enable | `false` |
| `HEADER_AUTH_USER_HEADER` | Header carrying the username | `X-Authentik-Username` |
| `HEADER_AUTH_EMAIL_HEADER` | Header carrying the email address | `X-Authentik-Email` |
| `HEADER_AUTH_NAME_HEADER` | Header carrying the display name | `X-Authentik-Name` |
| `HEADER_AUTH_AUTO_PROVISION` | Create an account when an unknown username arrives | `false` |
| `HEADER_AUTH_ALLOWED_DOMAINS` | Comma-separated email domain allowlist, empty allows any | empty |

The defaults are Authentik shaped. For an Authentik proxy provider you usually only need to set `HEADER_AUTH_ENABLED=true`, plus `HEADER_AUTH_AUTO_PROVISION=true` if you want first-login self-registration.

### Example: Authentik

```yaml
services:
  gitea-mirror:
    image: ghcr.io/raylabshq/gitea-mirror:latest
    environment:
      HEADER_AUTH_ENABLED: "true"
      HEADER_AUTH_AUTO_PROVISION: "true"
      HEADER_AUTH_ALLOWED_DOMAINS: "example.com,example.org"
```

### Example: Authelia

Authelia uses different header names, so override all three:

```yaml
services:
  gitea-mirror:
    image: ghcr.io/raylabshq/gitea-mirror:latest
    environment:
      HEADER_AUTH_ENABLED: "true"
      HEADER_AUTH_USER_HEADER: "Remote-User"
      HEADER_AUTH_EMAIL_HEADER: "Remote-Email"
      HEADER_AUTH_NAME_HEADER: "Remote-Name"
      HEADER_AUTH_AUTO_PROVISION: "true"
```

Then configure Authelia's authorization rules to protect the Gitea Mirror route and inject the `Remote-*` headers.

### How a user is resolved

1. An existing session cookie wins. Header auth only fires when there is no session, so users who signed in with a password or through SSO are unaffected.
2. The username header is matched against the `username` column.
3. If that finds nothing and an email header is present, the email is matched against the `email` column.
4. If neither matches and `HEADER_AUTH_AUTO_PROVISION` is `true`, a new account is created. When no email header is present the address falls back to `<username>@header-auth.local`.
5. If neither matches and auto-provisioning is off, the request is rejected and a warning is logged.

When `HEADER_AUTH_ALLOWED_DOMAINS` is set and an email header arrives, the email's domain must appear in the list or the request is rejected before any lookup happens.

### Security requirements

> **Warning:** Your reverse proxy must strip inbound copies of the configured headers from client requests before injecting its own. Without that, anyone who can reach the app can send `X-Authentik-Username: admin` and walk straight in.

Beyond stripping headers:

1. **Do not expose the port directly.** When header auth is on, only the trusted proxy should be able to reach Gitea Mirror. Bind it to an internal network.
2. **Terminate TLS at the proxy.** Headers travel in plaintext over whatever link carries them.
3. **Be conservative with auto-provisioning.** With it off you create accounts once, and the proxy just fills in sessions afterwards. That is the safer default for shared deployments.

### Confirming it is active

On the **Configuration > Access** page, the **Header Authentication** switch is on when the feature is live. It only shows the state; the environment variables control it. You can also check the API:

```bash
curl https://your-domain.com/api/auth/header-status
```

It returns `{"enabled": true, ...}` once the variables are set.

## Gitea Mirror as an OIDC provider

Gitea Mirror can also issue identities to other applications. The app has no page for OAuth applications; create one through the API with a `POST` to `/api/sso/applications`, sending `name` and `redirectURLs` as JSON, plus `type` set to `web` (the default) or `native`. The response carries the `client_id` and the `client_secret`, which is shown only once. `GET` lists the applications. `PUT /api/sso/applications?id={client_id}` changes its name, redirect URLs or `disabled` flag, and `DELETE /api/sso/applications?id={client_id}` removes it, along with the tokens it was given and the approvals people gave it.

Redirect URLs follow the OAuth rules for each type, and a refused one comes back as a 400 that says why:

- A **web** application needs an https URL on a real host name. `localhost`, `127.0.0.1` and `[::1]` are refused, as is plain http. An app that is only reachable over http on your network cannot be registered as it is; serve it over https, for example through your reverse proxy.
- A **native** application can use https on a real host name, plain http only on exactly `localhost`, `127.0.0.1` or `[::1]` (any port), or an app scheme named like a reverse domain, such as `com.example.app:/callback`.

The same rules apply when `PUT` changes the redirect URLs. A URL the application already has can stay, so an application registered by an older version keeps the addresses it was created with.

Like SSO providers, OAuth applications are managed by the instance owner only. That covers these calls and the auth library's own endpoints under `/api/auth/oauth2/` for creating, registering, listing, changing and deleting applications, dynamic client registration at `/api/auth/oauth2/register` included. An application can ask anyone on the instance to approve it, so one made by another account could pass itself off as a familiar service and collect approvals for that account. Everyone can still sign in to the applications the owner set up and manage their own approvals, and any signed-in account can look up one application with `GET /api/sso/applications?clientId={client_id}`, which the consent page uses. In earlier versions any account could create its own applications; those show up in the owner's list, so delete any you do not recognize.

The issuer is your `BETTER_AUTH_URL` followed by `/api/auth`, so set `BETTER_AUTH_URL` to the address the other applications use. With `BASE_URL` set, every URL below gets that prefix before `/api/auth`.

Standard endpoints:

| Purpose | URL |
|---|---|
| Discovery | `https://your-domain.com/api/auth/.well-known/openid-configuration` |
| Authorization | `https://your-domain.com/api/auth/oauth2/authorize` |
| Token | `https://your-domain.com/api/auth/oauth2/token` |
| UserInfo | `https://your-domain.com/api/auth/oauth2/userinfo` |
| JWKS | `https://your-domain.com/api/auth/jwks` |

Supported scopes are `openid` for the user ID, `profile` for name and username, `email` for the address and its verification status, and `offline_access` for a refresh token, which needs PKCE or an OIDC nonce. Users see a consent screen the first time an application asks for access.

## Troubleshooting

**Invalid origin errors.** `BETTER_AUTH_URL` does not match the URL users actually visit. Set it to the external origin, and list any other address you use in `BETTER_AUTH_TRUSTED_ORIGINS`.

**Redirected to the homepage with `?error=UNKNOWN` after a successful SSO login.** The upstream login worked but linking to the existing local account was refused. The usual cause is a Domain field that does not match the user's real email domain. Set `BETTER_AUTH_LOG_LEVEL=debug` to see the full callback trace, and look for a message about an account not being linked.

**Sent to an error page with `error=SIGNUP_CLOSED` after an SSO login.** The person has no account yet and their email is not in the provider's Domain. Add their email domain to the provider's Domain field, or set `AUTH_ALLOW_SIGNUP=true` to let anyone in. See [New accounts through SSO](#new-accounts-through-sso).

**Sent to an error page with `error=sso_callback_failed`.** The SSO callback threw an error, and `error_description` in the address bar carries its message. Set `BETTER_AUTH_LOG_LEVEL=debug` for the full trace.

**`TypeError: undefined is not an object (evaluating 'url.startsWith')`.** The stored provider record is missing its OIDC endpoints. Delete the provider and add it again using the **Discover** button so the endpoints are saved.

**Redirect loop on SSO.** The redirect URI registered upstream does not exactly match `/api/auth/sso/callback/{provider-id}`. Trailing slashes and http versus https both count as a mismatch.

**Header auth does nothing.** Confirm `HEADER_AUTH_ENABLED` is the string `"true"`, then check `/api/auth/header-status`. Also confirm the proxy is actually setting the header names you configured, since the defaults are Authentik specific.
